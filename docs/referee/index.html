Referee (Host) Server — Setup & Run

This page documents how to run the Referee (signaling/task) server that coordinates distributed compute and acts as the central "referee" for multi-client games.

Overview

The referee server is a lightweight Node.js process in the /server folder. It provides a WebSocket signaling endpoint and an HTTP /assign endpoint to distribute compute tasks to capable clients. Clients may advertise compute capability and benchmarks so the referee can select them.

AI Provider Requirements

The project supports multiple AI providers. The Referee server (and compute workers) can be configured to use one of the following:

  • Ollama (local host) — a self-hosted LLM host. Default base URL: http://localhost:11434. Endpoints used: /api/tags (models) and /api/generate.
  • OpenAI — cloud API using an API key. Used via the OpenAI SDK / REST endpoints.
  • Google Gemini — Google Generative Language API (requires API key).
  • Mock — in-development fallback for testing.

The code is provider-agnostic where possible — other local LLM hosts exposing compatible HTTP endpoints can also be used if configured accordingly.

Download packaged Referee server

A packaged zip of the server folder is available for download from this site at /server/referee-server.zip (created by CI). If not present, use the repository server folder on GitHub.

Run locally (from source)

  1. Clone the repository and change into the server directory: 
    git clone https://github.com/CJMoseley/T13NarrativeGameEngine.git
cd T13NarrativeGameEngine/server
  2. Install and start: 
    npm install
npm start
  3. Verify: http://localhost:3000/health should return { ok:true }.

Run with Docker (recommended for portability)

We can add a Dockerfile to the server package; if you want this packaged in the download, enable the Dockerfile option in CI. Example commands to run locally (assuming a Dockerfile present):

docker build -t t13-referee ./server
docker run -p 3000:3000 t13-referee

Configure AI provider for the referee/compute workers

Set the AI configuration either in a runtime config file or environment variables used by the server/worker. Example configuration object:

{
  "provider": "ollama", // or 'openai' / 'gemini' / 'mock'
  "baseUrl": "http://localhost:11434",
  "model": "llama3",
  "apiKey": "YOUR_API_KEY_IF_REQUIRED",
  "temperature": 0.7
}

Important: Ollama requires pulling a compatible model to your Ollama instance; consult Ollama docs.

Distributed compute model

Clients register over WebSocket with a JSON { type: 'register', clientId, info } message. They may send a benchmark message to advertise their capabilities (e.g., { computeCapable: true, cpu: 8, memoryGb: 16 }).

To assign work, POST to /assign with a JSON body containing a task object. The server will broadcast a taskAssign message to compute-capable clients or to all clients as a fallback.

Security and verification (notes)

  • The current prototype trusts clients and does minimal verification. For production you should add: result verification (Merkle-chunked digests), spot re-computation, client reputation/blacklisting, and TLS for transport.
  • Be mindful of LLM model licensing when distributing requests and results.

Troubleshooting

  • If AI calls fail, check which provider is configured and that the provider endpoint/API key is reachable and valid.
  • For Ollama, ensure the model is pulled and the Ollama daemon is running: ollama pull llama3 and ollama run.
